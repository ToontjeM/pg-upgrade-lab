PostgreSQL Upgrade Lab

Why staying current isn't optional

Three real reasons old PostgreSQL puts you at risk

Every major PostgreSQL release ships security hardening, performance work, and reliability improvements that you simply do not get by staying put. Each tab below runs the exact same setup against a genuinely old and a genuinely current PostgreSQL, side by side, with nothing mocked -- every result is a real command against a real running instance.

Security — PG14 vs PG18

Before PostgreSQL 15, any role that can merely CONNECT to a database can also create objects in its public schema by default — nobody has to grant that, it's just on.

Chained with an ordinary, idempotent deploy script, that's enough for a low-privileged app credential to make itself superuser.

PG15 revoked that default; PG18 inherits the fix.

This tab also runs a second scenario on PG15.5 vs PG15.6 — same story, but a minor-version patch (CVE-2024-0985), not a major upgrade.

Performance — PG17 vs PG18

PostgreSQL 18's B-tree indexes can skip over irrelevant values in a composite index's leading column, even when the query has no predicate on that column at all.

PG17 has no such capability, so it has to scan the whole index instead.

Confirmed live: PG17 touches ~112,000 buffer pages for this query; PG18 touches ~180. This tab runs it against both and shows the real counts Postgres reports.

Reliability — PG16 vs PG18

PostgreSQL 17 added logical replication slots that survive failover (sync_replication_slots).

Promote a standby on PG16 and every logical subscriber breaks — the slot never existed on that node, and fixing it means a manual, full resync.

On PG18 the slot just follows the standby — no resync required.
The pattern across all three: none of this requires exotic configuration or bad luck. It's what happens when perfectly ordinary operational practice meets a version that's a few years behind.
These scenarios are just examples. There are many more enhancements between major and minor versions of PostgreSQL than this lab can show hands-on. See the official release notes at postgresql.org/docs/release for the full list for any version.

Public-schema privilege escalation

A low-privileged role -- app_user, granted only CONNECT, the shape of a leaked application credential -- plants a trojan table+trigger in public. Later, the DBA's routine, idempotent deploy script (a CREATE TABLE IF NOT EXISTS + INSERT, the kind every team runs constantly) reuses that table without knowing it isn't theirs, firing the attacker's trigger inside their own superuser session.

On PG18, step 1 itself fails: PostgreSQL 15 revoked CREATE on public from PUBLIC by default, so the attacker never gets a foothold.

CVE-2024-0985: a minor-version fix, not a major one

        
REFRESH MATERIALIZED VIEW CONCURRENTLY is meant to run a view's own SQL as the view's
        owner, precisely so a privileged user can safely refresh a materialized view someone else created.
        Role r0 — an ordinary application role with its own database, nothing unusual granted
        — plants a materialized view that hijacks a brief moment where Postgres drops that protection while
        building its own internal temp table. An admin routinely refreshing that view is all it takes.

        
This isn't PG17 vs PG18 — both sides below are PostgreSQL 15. 15.6
        (released the same day as this fix, 2024-02-08) rejects the refresh outright; 15.5 silently makes
        r0 superuser. Staying current on minor releases matters as much as major ones -- see the
        note on the Overview tab.

B-tree skip scan

        
PostgreSQL 18 can jump over irrelevant values in a composite index's leading column instead of scanning
        every entry, even though the query below has no predicate on that leading column (tenant_id) at
        all -- only on the trailing one (serial_no), which has no index of its own. PG17 has no such
        capability, so it must scan the whole composite index instead.

        
This is an algorithmic win, not an I/O one, so -- unlike this tab's earlier async-I/O
        scenarios -- it doesn't need slow storage to show up: it's measured in buffer pages touched (Postgres's
        own count from EXPLAIN (ANALYZE, BUFFERS)), not milliseconds, and the gap is the same on fast
        local disk as anywhere else.

Failover-persistent logical replication slots

        
Each version has a primary, a streaming standby, and a logical subscriber reading a live publication.
        Clicking Simulate failover promotes the standby and repoints the subscriber at it -- exactly what an
        on-call engineer does during a real incident.

        
PG18 synchronizes the logical slot to the standby as it streams
        (sync_replication_slots), so it's already there once promoted -- replication just continues.
        PG16 has no such mechanism: the slot never existed on the standby, so the subscriber's worker dies with
        replication slot does not exist until someone manually recreates it and resyncs from scratch.
