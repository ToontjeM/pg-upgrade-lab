PostgreSQL Upgrade Lab

Why staying current isn't optional

Three real reasons old PostgreSQL puts you at risk

Every major PostgreSQL release ships security hardening, performance work, and reliability improvements that you simply do not get by staying put. Each tab below runs the exact same setup against a genuinely old and a genuinely current PostgreSQL, side by side, with nothing mocked -- every result is a real command against a real running instance.

Security — PG14 vs PG18

Before PostgreSQL 15, any role that can merely CONNECT to a database can also create objects in its public schema by default — nobody has to grant that, it's just on. Chained with an ordinary, idempotent deploy script, that's enough for a low-privileged app credential to make itself superuser. PG15 revoked that default; PG18 inherits the fix.

Performance — PG17 vs PG18

PostgreSQL 18 introduced asynchronous I/O (io_method): reads no longer have to block one at a time on storage. PG17 has no such setting at all. The benefit shows up specifically as storage latency goes up — this tab runs the same scans against both, live, and shows the real numbers, good or bad.

Reliability — PG16 vs PG18

PostgreSQL 17 added logical replication slots that survive failover (sync_replication_slots). Promote a standby on PG16 and every logical subscriber breaks — the slot never existed on that node, and fixing it means a manual, full resync. On PG18 the slot just follows the standby, no resync required.

The pattern across all three: none of this requires exotic configuration or bad luck. It's what happens when perfectly ordinary operational practice meets a version that's a few years behind.

Public-schema privilege escalation

A low-privileged role -- app_user, granted only CONNECT, the shape of a leaked application credential -- plants a trojan table+trigger in public. Later, the DBA's routine, idempotent deploy script (a CREATE TABLE IF NOT EXISTS + INSERT, the kind every team runs constantly) reuses that table without knowing it isn't theirs, firing the attacker's trigger inside their own superuser session.

On PG18, step 1 itself fails: PostgreSQL 15 revoked CREATE on public from PUBLIC by default, so the attacker never gets a foothold.

Asynchronous I/O

        
PostgreSQL 18 can issue multiple reads at once instead of blocking one at a time (io_method =
        worker or io_uring); PG17 has no such setting. Both nodes here share the same
        shared_buffers and the same 768MB container memory cap against a ~3.75GB table, so scans are
        genuinely I/O-bound rather than served from cache.

        
Be aware: AIO's benefit is hiding storage latency. On fast local disk (which
        is what this laptop/Docker Desktop gives both containers) that latency barely exists, so a live run here may
        show a small gain, no difference, or occasionally PG18 slightly behind -- that's an honest result, not a
        broken demo. The gap is real and larger on the network-attached storage typical of production and cloud
        databases -- turn up Disk throughput below to simulate that and open the gap back up.

Failover-persistent logical replication slots

        
Each version has a primary, a streaming standby, and a logical subscriber reading a live publication.
        Clicking Simulate failover promotes the standby and repoints the subscriber at it -- exactly what an
        on-call engineer does during a real incident.

        
PG18 synchronizes the logical slot to the standby as it streams
        (sync_replication_slots), so it's already there once promoted -- replication just continues.
        PG16 has no such mechanism: the slot never existed on the standby, so the subscriber's worker dies with
        replication slot does not exist until someone manually recreates it and resyncs from scratch.
